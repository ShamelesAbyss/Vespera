# Bounded workflow orchestration

`vespera-orchestrator` executes operator-authored sequential workflows through the real agent, scheduler and provider interfaces. It is available through the library API and the native `run-workflow` command; see [CLI.md](CLI.md) and the [strict JSON example](../config/workflow.example.json). It does not ask a model to invent a plan or interpret generated text as control-plane authority.

## Execution and authorization

Construct `Orchestrator::new(agent_runtime.clone())`, then call `execute(workflow, cancellation_token).await`. The returned `WorkflowReport` contains a terminal root task, attempt records, accepted contributions, token reservations, failure/evaluation evidence and selected step. `selected_result()` returns a contribution only for a completed workflow. `report(task_id)` inspects in-process history; `forget(task_id)` explicitly removes terminal workflow history. It cannot remove running work or agent history.

The coordinator must be a registered idle agent with `Permission::Delegate`. Each step has explicit capability requirements and an ordered candidate-agent allowlist. Routing selects an idle candidate whose current model policy resolves to a healthy compatible registration. Suspended/failed agents are never resumed automatically. Every actual task is accepted through the agent runtime's permission-checked delegation API. Only eligible candidate providers are health-polled before each attempt, including after prior evidence expires. Model activation remains scheduler-owned; there is no activation of all inventory or inference in the coordinator just to route work.

The root task's required capabilities must be covered by the step requirements. This is structural validation, not automatic natural-language requirement inference. Dependencies must refer to earlier steps, preventing cycles and ambiguous execution order. Each step receives JSON containing the operator request, step instructions and explicitly labeled untrusted dependency outputs with task/agent/model provenance. That text cannot edit the authored plan, grants, identity or routing policy. No tools execute.

An optional [scheduler latency preference](SCHEDULER.md#observed-latency-preference)
can rank eligible models for a capability-based worker using completed calls
in the same runtime. The workflow still chooses agents from the authored
candidate order and records both the candidate and the actual result model.

## Bounds and failure semantics

| Boundary | Implemented limit |
| --- | --- |
| Retained/running workflows per orchestrator | 8; explicit terminal forgetting required when full |
| Steps per workflow | 1–16 |
| Authored root + step prompt text | At most 64 KiB total |
| Expanded prompt per attempt | At most 64 KiB, including serialized dependency results |
| Candidate agents per step | 1–32 distinct IDs |
| Capabilities per step | 1–32 validated slugs |
| Attempts per step | 1–3 |
| Attempt budget per workflow | 1–48 |
| Output token budget per workflow | 1–1,048,576 sum of requested bounds |
| Accepted generated bytes per workflow | At most 1 MiB across attempts |
| Whole-workflow and per-step deadline | 1–3,600,000 ms, independently enforced |

Output token accounting reserves the requested maximum before every delegated attempt, including failures. It never substitutes an unknown token count with a fabricated measurement. Actual accepted output and provider-reported metrics remain separately recorded. Logical retention bounds exclude allocator overhead and caller-owned clones. The default history lives in the process.

A failure halts subsequent steps and preserves previous contributions. Only explicit HTTP 429/503 inference rejections are eligible for bounded retry. Retry routing considers remaining idle candidates; it does not clear a failed identity or retry uncertain timeouts. Exhausted attempts/tokens, no suitable candidate, resource admission failure, delegation denial and execution failure are distinct report categories. Empty/whitespace-only output is retained as execution evidence but fails workflow evaluation.

Caller cancellation, whole-workflow expiry, per-step expiry and dropped/aborted futures produce terminal local history and release owned inference leases. An ownership guard cancels queued delegation if execution never starts. Cancellation does not prove remote compute stopped; provider reservations and uncertainty remain managed by the scheduler. The orchestrator does not shut down a shared scheduler or unload models when one workflow ends.

## Durable workflow history

Pass `--workflow-store <PATH>` to commit checkpoints in a private local SQLite
file. The workflow commits its authorized plan and root identity, records
the intended attempt before delegation, records acceptance before inference,
and commits each outcome before retries or dependent work. A failed checkpoint
stops advancement. The file holds up to 16 workflows with a 1 MiB plan limit
and a 32 MiB report limit per workflow. Use a separate file when this capacity
is reached. The database contains prompts, generated content and provenance.

Use `workflow-history --database <PATH> --task <UUID>` after the invocation
exits. It opens an existing database exclusively and prints the stored plan,
report and interruption flag without provider access. A retained running
checkpoint is reported as interrupted. Its last observed task states are
preserved, including any attempt with an unknown outcome. A duplicate root
ID is rejected before provider access when reusing the same database.
Inspection and duplicate fencing are available. Resuming execution from a
safe checkpoint remains open.

## Output policies and conflicting contributions

`OutputPolicy::Step { step }` selects an explicitly named successful contribution. `OutputPolicy::Agreement { steps, on_conflict }` compares complete generated strings byte-for-byte. Matching strings select the first named contribution. Disagreement records all compared step names; `ConflictPolicy::Fail` fails the workflow, while `ConflictPolicy::Prefer { step }` applies the operator's declared precedence and preserves every contribution. The report retains the output policy.

A selected output is not a statement that its claims are correct. There is no semantic judge, factual verifier, automatic conflict synthesis or arbitrary generated evaluation code. Length-limited responses preserve their provider finish reason; agreement is not semantic equivalence.

## Verification and remaining integration

```powershell
cargo test -p vespera-orchestrator --locked
cargo test -p vespera-orchestrator --release --locked
```

Twelve integration tests exercise actual native HTTP adapter payloads through agent/registry/scheduler composition: single/dependent work, selected model activation, provenance, ownership/permissions, capability misses, resource exhaustion, partial failure, attempt/token bounds, rejection retries, exact agreement/conflict precedence, empty output, cancellation/expiry/abort, strict plan fields and bounded history. They require no installed model and do not constitute live multi-model interoperability evidence.

Application composition scopes named agents and eligible worker inventory; executable fixtures cover both adapters, denied/invalid input, command deadlines, unchanged configuration and delegation-only coordinator isolation. One native live two-step sample is recorded in [the artifact](../artifacts/live-workflow-2026-11-06.json). Automatic task decomposition, richer resource/context-aware candidate ranking, durable parent/child history and event publication remain future work. See [architecture](ARCHITECTURE.md), [agents](AGENTS.md), [scheduler](SCHEDULER.md), [roadmap](ROADMAP.md) and [development log](DEVELOPMENT_LOG.md).
